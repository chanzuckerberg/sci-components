MCP Server

@czi-sds/mcp is the official Model Context Protocol server for the Science Design System. It gives an AI coding agent first-hand knowledge of SDS — every component's props, its written documentation with runnable examples, and the full set of design tokens — so the agent writes code against what the library actually exposes instead of guessing from its training data.

The Model Context Protocol is an open standard for connecting assistants to external tools and data. Any MCP-capable client can use this server: Cursor, Claude Code, Claude Desktop, VS Code, and others. See modelcontextprotocol.io for the protocol itself.

Why use it

Without the server, an agent asked to "add an SDS button" will reach for props that sound plausible. SDS components are thin wrappers over Material UI with their own sdsType, sdsStyle and sdsSize vocabulary, and that vocabulary differs per component. The server closes the gap in three ways:

  • Correct props. The agent can read the real prop list for a component, with resolved types, defaults and descriptions, before it writes a line.

  • Real examples. Component documentation arrives with the same code examples rendered on the component's Documentation tab in this Storybook, so generated code follows house patterns.

  • Design tokens, not hardcoded values. The agent can look up the Tailwind token for a color or spacing step rather than inventing a hex value.

What it serves

Four tools the agent can call, and three resources it can read for standing guidance. Both are covered in full on the Tools and Resources page.

Tool

What it returns

list_components

Every component name in both SDS packages.

get_component_props

One component's props, with types, defaults, descriptions and which subcomponent each belongs to.

get_component_docs

One component's written documentation as Markdown, including how it differs from MUI and a runnable example per variation.

get_tailwind_tokens

Design tokens as Tailwind utilities, all of them or one category at a time.

How the data is built

The server ships its answers rather than computing them. Everything under data/ is generated from this repository at build time and published inside the package, so a request costs a file read and no network call at all — and the answers always describe the version of SDS you installed, not whatever is on main.

Generated file

Built from

component-list.json

The exports of each package's src/core.

component-props/

Each component's TypeScript source, resolved by the compiler, narrowed to the props its Storybook argTypes declare and enriched from the props tables in its documentation.

component-docs/

Each component's __storybook__/docs/content.html converted to Markdown, with the source of every live example inlined.

tailwind.json

The Style Dictionary token build.

The practical consequence is that the documentation an agent reads is the same documentation you are reading now. There is no second copy to drift.

Transports

STDIO is the primary transport and what every editor integration uses: the client spawns the server as a child process and talks to it over standard input and output. HTTP is also available via yarn mcp:serve, for web integrations that cannot spawn a process.
