Installation

The server is published to npm as @czi-sds/mcp and speaks the STDIO transport, which means there is nothing to install and nothing to keep running. You point your editor at a command, and the editor starts the server as a child process whenever it needs it. Its source lives in packages/mcp on GitHub.

Every client below is configured with the same three values, so if yours is not listed, these are what its own documentation will ask for:

Setting

Value

Transport

stdio

Command

npx

Arguments

-y @czi-sds/mcp

Node 22 or newer is required. The -y flag lets npx fetch the package without prompting the first time; after that it is cached.

Cursor

Add the server to .cursor/mcp.json in the project you want it available in, or to ~/.cursor/mcp.json to enable it everywhere.

Cursor picks the file up without a restart. Confirm it connected under Settings → MCP, where sds should be listed with its four tools.

Register it from the command line, from inside your project:

Add --scope user to make it available in every project rather than just this one. Run claude mcp list to check that it connected.

Claude Desktop

Edit the configuration file for your platform:

Platform

Path

macOS

~/Library/Application Support/Claude/claude_desktop_config.json

Windows

%APPDATA%\Claude\claude_desktop_config.json

Claude Desktop reads this only at launch, so quit and reopen it. The tools appear under the attachments menu in a new conversation.

VS Code

Add .vscode/mcp.json to the workspace. Note that VS Code uses servers where the others use mcpServers.

Pinning a version

npx -y @czi-sds/mcp resolves to the latest published version. The data the server returns describes the SDS release it was built from, so if your application is pinned to an older @czi-sds/components, pin the server to match and the agent will stop suggesting props you do not have yet:

Running from a local build

Contributors working on the server itself should run it out of the repository instead, so changes take effect on rebuild.

yarn mcp:build regenerates everything under data/ before bundling, which is what makes the built server reflect your working tree. Then point the client at the built entry point using an absolute path:

Give it a distinct name such as sds-local so it does not collide with a published copy you may already have configured. Rebuild with yarn mcp:build after each change, and restart the client to pick it up.

Checking that it works

The quickest confirmation that the package runs at all, independent of any editor:

The second command omits -y on the inner npx on purpose: the inspector claims every flag it recognises before the command, so a -y there would be read as the inspector's own and the server would never start. The first command is what gets the package cached so it is not needed.

A successful run prints the four tool definitions as JSON. If it does, any failure after this point is in the client's configuration rather than the server. The Testing with the Inspector page covers the inspector in full.

Inside a client, ask the agent something only the server can answer, such as "list the SDS components" or "what props does the SDS Callout take?", and watch for a tool call in the transcript.
