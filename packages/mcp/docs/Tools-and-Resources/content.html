Tools and Resources

The server exposes two kinds of thing. Tools are functions the agent calls when it needs an answer, and there are four of them. Resources are documents the agent reads for standing guidance, and there are three. Everything is served from files generated at build time, so calls are local and immediate.

list_components

Every component name in both SDS packages. This is usually the agent's first call, because the other two component tools accept only names from this list.

The two keys correspond to the two published packages, @czi-sds/components and @czi-sds/data-viz, which tells the agent which one to import from.

get_component_props

One component's props: the resolved TypeScript type, whether it is required, its default, and a description. Reach for this when the agent needs to know what it may pass; reach for get_component_docs when it needs to know how the component is meant to be used.

Parameter

Type

Required

Description

component

enum

Yes

A component name. The enum is built from the component list, so an invalid name is rejected before the tool runs.

The response is keyed by component, not by prop, because a prop set often spans a component and its subcomponents. In the example above, subtitle belongs on <AccordionHeader> rather than <Accordion>, and the grouping is what tells the agent where to put it.

Only the props a component genuinely means to expose are listed, the ones its Storybook argTypes declare, rather than the hundreds each component inherits from Material UI. A type of any means the prop is a Storybook-only control that drives the demo rather than a real prop.

get_component_docs

A component's written documentation as Markdown: what it is for, how it differs from the MUI component underneath, its props table, and a complete runnable example for every supported variation. This is the same content as the Documentation tab on the component in this Storybook.

Parameter

Type

Required

Description

component

enum

Yes

A component name. The enum covers only components that have a documentation page, which is a smaller set than list_components returns.

These are the longest responses the server produces, with Callout's running to roughly 13,000 characters, because each example is inlined in full rather than summarised. That is deliberate: an agent that has read a working example writes code in the same shape.

get_tailwind_tokens

The design tokens, expressed as the Tailwind utilities that map to them, so the agent reaches for text-sds-body-s rather than a raw pixel value.

Parameter

Type

Required

Description

category

enum

No

One of colors, spacing, typography, fontFamily, fontSize, fontVariantNumeric, letterSpacing, lineHeight, textDecoration, textTransform, height, width, borderRadius, boxShadow, breakpoints, or all. Defaults to everything.

The response comes in two parts: prose guidance on how to use that family of tokens, then the tokens themselves as JSON. Guidance is written for five categories, namely colors, typography, spacing, borderRadius and boxShadow. The rest return a short note saying so, followed by their tokens as usual.

Asking for everything at once returns a large payload, so prefer a category when you know which one you need.

Resources

Resources are Markdown documents the client can pull into context, addressed by URI. Unlike tools they take no arguments and are not called mid-task. They are standing instructions, best attached at the start of a session so they shape everything the agent writes afterwards.

URI

Contents

sds://rules/components

How to use SDS components correctly: which to choose, how to compose them, and the mistakes worth avoiding.

sds://rules/figma

How to translate a Figma design into SDS code, mapping frames and layers onto the components and tokens that implement them.

sds://rules/documentation

How to read what the documentation tools return, and how to treat it as the source of truth over prior assumptions about the library.

Clients surface resources differently: Claude Desktop lists them under the attachments menu, while others expose them through a resource picker or attach them automatically. Check your client's documentation if you cannot find them.

Using them together

The tools are designed to chain, and an agent given a real task will generally walk them in this order:

  1. list_components to find out what exists and what it is called.

  2. get_component_docs to learn the intended usage and copy the shape of a working example.

  3. get_component_props to confirm the exact props, types and defaults before writing them.

  4. get_tailwind_tokens for any spacing, color or type value the component does not supply itself.

You rarely need to direct this. Naming the design system in the request is usually enough: "build a settings panel using SDS" will pull in what it needs. Where it helps to be explicit is in correcting course: if the agent writes a prop that does not exist, telling it to check the component's props against the MCP server is faster than describing the right answer yourself.
